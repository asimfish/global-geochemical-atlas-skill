### P04-DEF-004：错误协议与 P01 不兼容

- 优先级：P0
- 状态：`OPEN`
- 现象：
  - P04 使用 `layer=data_acquisition`，P01 只允许 `input/source/skill/artifact/scorer/runner`。
  - P04 内部错误码与 P01 公共错误码没有重合。
  - P04 错误对象缺少 `retryable`、`stage`、`attempt`、`cause_exit_code` 和 `evidence`。
  - `eval.download.acquire` 对所有 P04Error 返回退出码 2，而 P01 将退出码 2 定义为 `PARTIAL_SUCCESS`。
- 影响：P02/P06 如果直接使用 P04 CLI 退出码，会把数据获取失败错误归类为部分成功，导致统计和重试归因错误。
- 建议映射：
  - 403/权限拒绝 → `SOURCE_ACCESS_DENIED` / 11。
  - 下载、断网、hash、MIME、缓存损坏 → `SOURCE_DOWNLOAD_INVALID` / 12。
  - Schema、字段、版本和适配器变化 → `SOURCE_FORMAT_CHANGED` / 13。
  - P04 自身未捕获异常 → `RUNNER_INTERNAL_ERROR` 或经 P02 适配后的冻结错误。
- 关闭条件：
  1. 建立版本化的 P04→P01 错误映射表。
  2. 明确映射责任位于 P04 adapter 还是 P02 gateway，禁止两边各自解释。
  3. 产出完整 P01 error 对象并通过 `result.schema.json`。
  4. 为每类内部错误增加公共 code/exit/layer 契约测试。

### P03-DEF-002：严格 deadline + grace 上界失效

- 优先级：P0
- 状态：`OPEN`
- 现象：有效计划 `stage_timeout_seconds=0.15`、`termination_grace_seconds=0.2` 的理论上界为 0.35 秒；SIGTERM-resistant fixture 实测总耗时 0.496 秒，超出 0.146 秒。上一轮五次复测耗时约 0.431–0.531 秒，均超过严格上界。
- 根因线索：终止后仍执行 `/proc` 全量刷新、子进程回收、两个日志线程各最多 0.5 秒 join、outcome 解析与 snapshot/status 写入；现有测试还额外容许 0.2–0.25 秒，弱化了计划中的硬验收条件。
- 影响：短 deadline/grace 计划不能兑现结束上界；正式 43,200 秒预算末端也可能产生不可解释的超时外运行。
- 关闭条件：
  1. 使用单一绝对 `shutdown_deadline = workload_deadline + grace` 约束 TERM、KILL、wait、pipe drain 和必要收尾。
  2. 超过 shutdown deadline 后不得继续阻塞；非关键 snapshot 丰富化应异步/限时或记录为降级证据。
  3. 将测试断言收紧为 `elapsed <= deadline + grace +` 明确且很小的时钟/调度误差，不得再增加第二个 grace。
  4. 对正常 TERM、忽略 TERM、daemonized child 和高 PID 数四种路径重复压力测试，无残留进程且上界稳定通过。

### P03-DEF-004：超时 SIGTERM 被误分类为取消

- 优先级：P0
- 状态：`OPEN`
- 现象：P03 在 `STAGE_TIMEOUT`/`GLOBAL_TIMEOUT` 后用 SIGTERM 清理 workload，stage report 因而记录 `signal=15`。P02 `_public_exit` 当前先判断 `signum in {2, 15}` 并返回 `RUNNER_CANCELLED`/76，之后才判断 timeout classification；直接调用复现结果为 `(76, 15)`。
